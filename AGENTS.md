# Agent Instructions for gsm.viz

This file guides AI agents working in this repository: GitHub Copilot CLI, the Copilot cloud agent, Copilot PR code review, and any other agent that reads `AGENTS.md`. It is the single source of agent instructions. `CLAUDE.md` is a symlink to this file so Claude Code shares the same instructions. There is no `.github/copilot-instructions.md`.

## Project Overview

**gsm.viz** is a web-based JavaScript data-visualization library by Gilead BioStats for clinical trial risk-based monitoring (RBM). It renders generic spec-driven bars and faceted bars, points and faceted points, plus KRI-specific bar charts, scatter plots, time series, sparklines, and group overviews — built on **Chart.js 3** and **D3 7**.

| Layer | Technology |
|---|---|
| Language | JavaScript (ES modules) |
| Charting | Chart.js 3, D3 7 |
| Chart.js plugins | chartjs-plugin-annotation, chartjs-plugin-datalabels, @sgratzl/chartjs-chart-boxplot |
| Bundler | esbuild (`src/main.js` → `index.js`) |
| Testing | Jest 29 + jest-environment-jsdom + jest-canvas-mock |
| Transpilation | Babel (preset-env) |
| Formatting | Prettier — single quotes, tab width 4 |
| Deployment | gh-pages |

## Commands

```bash
npm run build          # Bundle + format + test + link bundles (full build)
npm run bundle         # esbuild: src/main.js → index.js (+ sourcemap)
npm test               # Jest test suite
npm run test:coverage  # Jest with coverage report
npm run format         # Prettier: format src, examples, tests
npm run local          # live-server dev server
npm run watch          # esbuild watch mode
npm run deploy         # Deploy examples to gh-pages
```

For chart modules, `<module>.js` is the entry point and `<module>/` contains the module internals.

### Module Pattern

Each chart type follows a consistent pattern:

- **Entry file** (`src/<chartType>.js`) — exports the public API
- **Module directory** (`src/<chartType>/`) — contains internal implementation files
- **Data transforms** — pure functions that process input data
- **Config builders** — functions that produce Chart.js or D3 configuration objects
- **Chart renderers** — functions that render charts to canvas/SVG via Chart.js or D3
- **Documentation** — module docs in `examples/docs/` must be updated whenever new functionality, configuration options, mappings, helpers, or public behavior are added to a module

Generic modules (`bars`, `facetBars`, `points`, and `facetPoints`) take `(element, data, spec)` with a ggplot2-inspired spec. They validate and merge it through `defaults.js`, `validateSpec.js`, and `mergeSpec.js`; `points` and the `facetPoints` validator also reject unsupported spec fields instead of ignoring them. KRI-specific modules (`barChart`, `scatterPlot`, `timeSeries`, `sparkline`, `groupOverview`) validate KRI-specific schemas through `src/data/`. Put new generic charting behavior in the generic modules, not the KRI-specific ones.

## Per-Module Scoping Rules

When reviewing a PR, **limit findings to the modules the PR actually touches**. Do not flag issues in unrelated modules.

### `src/scatterPlot*` · `tests/scatterPlot*`
- Review: data transform correctness in `structureData.js`; scale/axis configuration; tooltip and annotation plugin config; input validation logic.
- Expect tests in: `tests/scatterPlot/`
- Do not flag: behaviour of `barChart`, `timeSeries`, or any other unrelated module.

### `src/barChart*` · `tests/barChart*`
- Review: data structuring and `scriptableOptions` callbacks; annotation and datalabel plugin config; scale setup; input validation.
- Expect tests in: `tests/barChart/`
- Note: `barChart` is the KRI-specific bar implementation. New generic bar features should go in `bars`.

### `src/bars*` · `tests/bars*`
- Review: spec validation (`validateSpec`, `mergeSpec`); dynamic category logic in `getPlugins/`; data aggregation and axis-swap in `structureData/`; export functionality.
- Expect tests in: `tests/bars/`
- Flag: any change to `defaults.js` that could silently alter existing chart behaviour.

### `src/points*` · `tests/points*`
- Review: spec validation and immutable merging (`validateSpec`, `mergeSpec`, `defaults`); coordinate/log-scale validation in `structureData`; aesthetic styling (color, size, opacity, shape) and legends; tooltips and callbacks receiving the full source row; annotations and point labels; keyed selection, `updateData`/`updateSpec`, zoom, and export helpers; accessibility.
- Expect tests in: `tests/points/`
- Flag: invalid coordinates silently dropped instead of failing; new spec fields accepted without implemented behavior; changes to `defaults.js` that could alter existing charts.
- Do not flag: KRI-specific `scatterPlot` behaviour (`points` intentionally leaves it untouched).

### `src/facetBars*` · `src/facetPoints*` · `tests/facet*`
- Review: facet validation, ordering, and grid rendering; shared (fixed) vs free scale domains; global legend/style domains; synchronized legend, hover, and selection across child charts (mirrored updates must be silent); child helper updates after facet composition.
- Expect tests in: `tests/facetBars/` and `tests/facetPoints/`

### `src/timeSeries*` · `tests/timeSeries*`
- Review: line/point/distribution data structuring; threshold and interval line logic; scale and plugin (annotation, tooltip, legend, title) config; selected-group update path.
- Expect tests in: `tests/timeSeries/`

### `src/sparkline*` · `tests/sparkline*`
- Review: data structuring and `scriptableOptions`; annotation plugin (value line + thresholds); scale and plugin config; input validation.
- Expect tests in: `tests/sparkline/`

### `src/groupOverview*` · `tests/groupOverview*`
- Review: D3 table construction (`makeTable/`); column definition logic (`defineColumns/`); traffic lighting, sorting, row highlighting, and click events; data structuring and group-metric derivation.
- Expect tests in: `tests/groupOverview/`

### `src/data*` · `tests/data*` — ⚠️ SHARED
- **Elevated scrutiny.** Changes here affect every chart module that imports from `src/data/`.
- Flag: any change to `checkInput.js` or the data schema (`data/schema/`) that could silently break consumers.
- Require: tests that cover all affected data shapes.
- Expect tests in: `tests/data/`

### `src/util*`  — ⚠️ SHARED
- **Elevated scrutiny.** Utilities here are used across multiple modules.
- Flag: behaviour changes to any utility without a corresponding test update.
- Flag: new utility functions added without tests.
- Expect tests in: `tests/util/`
- Note: adding new utilities or modifying existing ones requires explicit discussion (ask-first territory).

### `examples/docs*`
- Flag: a PR that adds new public API, configuration options, or chart behaviour but does **not** update the relevant doc file in `examples/docs/`.

### `.github/workflows*`
- Flag: removal of test or build steps from CI; workflows that do not install dependencies before running tests.

### Generated bundles
- **Ignore during code review:** `index.js`, `index.js.map`, `examples/index.js`, and `examples/index.js.map` are generated by esbuild and are committed release artifacts.
- Do not comment on generated bundle or source-map diffs, including apparent direct edits. Review their `src/` inputs instead.
- Source changes that affect a bundle must still run `npm run bundle` so these artifacts remain synchronized.

### `index.js`
- Generated by esbuild from `src/main.js`; implementation work must not edit it by hand.

## TDD Compliance (mandatory)

**All code changes MUST follow Red/Green/Refactor TDD. This is a non-negotiable project rule** — every PR that changes implementation code must include a new or updated test.

### The Cycle

```
1. RED    — Write a failing test that describes the expected behavior
2. GREEN  — Write the minimum code to make the test pass
3. REFACTOR — Clean up the implementation while keeping tests green
4. VERIFY — npm test passes, npm run bundle succeeds
5. COMMIT — Save progress with a descriptive message
```

### Rules

- **No implementation code without a failing test first.** Write the test, see it fail, then implement.
- **Bug fixes require reproduction tests.** Write a test that demonstrates the bug (Red), then fix it (Green). This is the Prove-It Pattern.
- Tests live in `tests/<module>/` and mirror `src/` paths.
- Test framework: Jest with jsdom environment and jest-canvas-mock.
- **Flag** any implementation change (new function, modified logic, bug fix) that has no corresponding change in `tests/`.
- **Scope:** TDD applies to `src/`. `examples/` are demonstrations only and do not need tests.
- **Flag** any removed or skipped test (`test.skip`, `xit`, deleted file) without explanation.
- **Tests are evidence.** "It works" is not sufficient — a passing test suite is required proof. Run `npm test` after every change.

Test distribution target:
- ~80% unit tests on pure functions (data transforms, config builders, utilities)
- ~15% integration tests (rendering pipelines, data pipelines)
- ~5% E2E (full chart render with real data)

### Testing Configuration

- **Jest config:** `jest.config.js`
- **Canvas mock:** `jest-canvas-mock` (setup file, required for Chart.js)
- **Environment:** jsdom (default)
- **Ignored paths:** `/app/`, `/examples/`, `/node_modules/`
- **Test files:** Located in `tests/` directory

## Code Conventions

- **ES modules** — use `import`/`export`; no CommonJS `require`.
- **camelCase** for all file names and variable names.
- **Global export:** `gsmViz` (via esbuild `--global-name`)
- **Formatting** — Prettier handles it automatically (single quotes, tab width 4). **Do not flag** whitespace, quote style, or indentation — these are enforced by the formatter on commit.
- **Flag:** mixing `import`/`export` with `require`; PascalCase or snake_case file names; magic numbers or hardcoded strings with no explanatory comment.

## Core Operating Behaviors

These apply at all times, across all tasks:

1. **TDD Always** — Write failing test first, then implement. No exceptions.
2. **Surface Assumptions** — State assumptions explicitly before implementing. Don't silently fill in ambiguous requirements.
3. **Manage Confusion** — Stop when confused. Name the confusion. Ask. Don't guess.
4. **Push Back** — Point out problems directly. Sycophancy is a failure mode.
5. **Enforce Simplicity** — Prefer the boring, obvious solution. If 100 lines suffice, don't write 1000.
6. **Scope Discipline** — Touch only what the task requires. No unsolicited renovation.
7. **Verify with Evidence** — Tests passing, build succeeding. "Seems right" is never done.

## Development Workflow

Features ship through a fixed pipeline, with related work split into small issues and dependent changes delivered as stacked PRs when appropriate.

```
DESIGN ─→ ISSUES ─→ BRANCH + PR per issue ─→ PR STACK ─→ COPILOT REVIEW (≤ 3 rounds)
       ─→ HUMAN REVIEW ─→ MERGE to dev ─→ RELEASE CANDIDATE (dev → main)
```

Small fixes and isolated changes can skip Design and the PR stack: open one issue, one branch from `dev`, and one PR. They still go through the Copilot review loop and human review.

### Model Tiers

- **Design and decomposition** (steps 1–2): use a heavier, high-reasoning model. This model owns the API contract, sequencing, and acceptance criteria that every later step depends on.
- **Implementation and review response** (steps 3–5): use lighter, faster models, one issue per session. They implement against the issue's acceptance criteria and handle the Copilot review back-and-forth.
- **Escalate** to the heavier tier when implementation exposes a design flaw, such as a contract change, a new cross-issue dependency, or a scope change. Update the epic and affected issues instead of improvising in a PR.

### 1. Design

- Write an epic issue covering:
  - The problem and the consumers it blocks.
  - The proposed public API, with the spec shape and example usage.
  - The progressive scope.
  - What is out of scope or deferred.
- A human approves the design before sub-issues are created.

### 2. Issues

Break the epic into small, ordered, independently reviewable sub-issues with this structure:

```
<!-- <epic>-plan-id: P<n> -->

## Summary
<One-sentence outcome.>

## Proposed Solution
- <Modules/files touched and approach. Accept new public fields only in the issue that implements them — no no-op config.>

## Dependencies
- Depends on #<issue> (P<k>)        <!-- or "None" -->

## Acceptance Criteria
- [ ] <Observable, testable behavior>
- [ ] Docs (`examples/docs/`), examples, and NEWS updated where public behavior changes.
- [ ] Failing tests are observed before implementation; targeted tests, `npm test`, and `npm run bundle` pass.

## QC Approach
<Standard QC (code review + automated checks) plus any issue-specific qualification.>
```

### 3. Branch and PR per Issue

- One issue → one branch → one PR. Name branches `feature/<issue#>-<slug>` or `fix-<issue#>`.
- Branch from `dev`, or from the previous issue's branch when the work depends on it before it merges (see PR Stack).
- Implement with TDD (see TDD Compliance) in atomic commits, then run `npm test` and `npm run bundle`.
- Open the PR with `gh pr create --base <base-branch>` using the PR Description Template below.

### 4. PR Stack

When sub-issues depend on each other, stack their PRs. Each PR targets the previous PR's branch, and the first one targets `dev`. Add this block to each PR description:

```
<!-- <epic>-stack:start -->
## Stack

**Part <N> of <M>** for #<epic>.

- **Base:** `<base-branch>`
- **Head:** `<this-branch>`
- **Previous:** #<pr>                 <!-- or "Start of stack" -->
- **Next:** #<pr>                     <!-- or "End of stack" -->
- Review this PR against its listed base and merge the stack in order.
<!-- <epic>-stack:end -->
```

- Merge the stack in order. After a PR merges into `dev`:
  1. Retarget the next PR to `dev` with `gh pr edit <n> --base dev`.
  2. Bring `dev` into its branch (merge or rebase) and resolve conflicts.
  3. Rerun `npm test` and `npm run bundle`.
  4. Update the stack blocks on the affected PRs.
- Fix problems on the lowest PR they belong to, then propagate the fix up the stack. Do not patch them in a later PR.

### 5. Copilot Review Loop (required before ending a session)

An agent session that opens or updates a PR must run this loop before it ends:

1. **Request** a review with `gh pr edit <n> --add-reviewer "@copilot"` (keep the quotes; a bare `@copilot` is splatting syntax in PowerShell). Wait for `copilot-pull-request-reviewer[bot]` to post; poll `gh pr view <n> --json reviews` to check.
2. **Triage** every finding:
   - **Valid:** a bug, logic error, missing or incorrect test, contract or docs mismatch, accessibility gap, or security concern within this PR's scope.
   - **Not valid:** style-only, out of scope (it belongs to another issue in the stack), or factually wrong. Use the Per-Module Scoping Rules and Do Not Flag lists to decide.
3. **Fix** valid findings test-first, run `npm test` and `npm run bundle`, then commit and push.
4. **Reply** to every review thread with the fix commit SHA or the reason no change was made, then resolve the thread. Reply through the REST endpoint `repos/{owner}/{repo}/pulls/<n>/comments/<id>/replies`, and resolve through the GraphQL `resolveReviewThread` mutation.
5. **Re-request** a review (step 1) and repeat.

**Stop after 3 Copilot review rounds total** (the initial request plus at most two re-requests), or sooner if a round returns no valid findings. Then post one PR comment for the human reviewer that summarizes the rounds, the fixes made, the findings dismissed and why, and anything still open. Do not loop beyond 3 rounds; leave the remaining judgment calls to the human reviewer.

### 6. Human Review

- A human reviews and approves every PR. Agents never merge their own PRs.
- Human review feedback overrides Copilot findings. A session that addresses human feedback ends with a new Copilot review loop, which gets a fresh 3-round budget.

### 7. Release Candidate

- When `dev` is ready to release, open a release-candidate PR targeting `main`, either from `dev` directly or from an `rc-vX.Y.Z` branch cut from `dev`. Title it `vX.Y.Z` or `Release Candidate: gsm.viz vX.Y.Z`.
- The RC bumps the `package.json` version, finalizes `NEWS.md`, and regenerates bundles. It is the **only** kind of PR that targets `main`.
- After the release, merge `main` back into `dev` so the branches don't diverge.

### PR Description Template

```
## Summary

<Short description of what this PR does and why.>

## Changes

- <Bullet list of notable changes>

<Stack block, if the PR is part of a stack>

## Resolved Issues

- Resolves #<issue-number>
```

Include a `Resolves #NNN` or `Closes #NNN` line for every issue the PR addresses. GitHub closes issues automatically only when the PR merges into `dev`, the default branch, so retarget stacked PRs to `dev` before merging.

## Hard Boundaries — Always Flag

| Violation | Why |
|---|---|
| PR targets `main` instead of `dev` (other than a release-candidate PR from `dev` / `rc-vX.Y.Z`) | Only release candidates target `main` |
| Stacked PR includes changes that belong to a different issue in the stack | One issue per PR; fix on the lowest applicable branch |
| New `npm` dependency added without discussion | Requires team approval; check for prior issue/comment |
| Implementation change with no test | Violates the mandatory TDD rule |
| Failing test removed or permanently skipped | Masks regressions |
| Secrets, credentials, or real patient/clinical data committed | Hard security violation |

## Do Not Flag

- Prettier formatting details (quotes, semicolons, indentation) — the formatter handles it.
- Comment style or quantity — only flag if a comment is actively misleading.
- Variable name micro-choices that are within camelCase convention.
- Changes in `examples/` that are purely cosmetic demo updates with no API impact.
- Missing tests for `examples/` code — examples are demonstrations and are not tested.

## Boundaries

### Always Do

- Write a failing test before implementation (TDD)
- Run `npm test` before commits
- Run `npm run bundle` before commits to keep `index.js` in sync with source (a pre-commit hook enforces this automatically via Husky)
- Follow existing module patterns in `src/`
- Update the relevant module documentation in `examples/docs/` whenever adding new functionality or public behavior
- Use Prettier formatting (single quotes, tab width 4)
- Write descriptive commit messages with type prefixes
- Keep changes small (~100 lines per commit)
- Follow the Development Workflow: one issue → one branch → one PR, stacked when dependent
- Run the Copilot review loop (up to 3 rounds) before ending any session that opened or updated a PR

### Ask First

- Adding new dependencies
- Changing build configuration (esbuild, Babel)
- Modifying shared utilities (`src/util/`, `src/data/`)
- Changing the Jest configuration
- Creating new chart type modules
- Changing an approved design or issue's acceptance criteria mid-implementation (escalate instead)

### Never Do

- Commit secrets, credentials, or real clinical data
- Edit bundled output (`index.js`) directly
- Remove failing tests without approval
- Skip TDD for any code change
- Push to `main` without review
- Open PRs targeting `main`, except release-candidate PRs from `dev` or an `rc-vX.Y.Z` branch
- Merge your own PR, or continue the Copilot review loop past 3 rounds
