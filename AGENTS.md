# AGENTS.md

This file provides guidance to AI coding agents when working with code in this repository.

## Project Overview

**gsm.viz** (v2.3.0) is a web-based data visualization library by Gilead BioStats for clinical trial risk-based monitoring (RBM). It provides interactive charts — scatter plots, bar charts, time series, sparklines, site overviews, and group/country overviews — built on Chart.js and D3.

## Tech Stack

| Layer            | Technology                                                                           |
| ---------------- | ------------------------------------------------------------------------------------ |
| Language         | JavaScript (ES modules)                                                              |
| Charting         | Chart.js 3, D3 7                                                                     |
| Chart.js Plugins | chartjs-plugin-annotation, chartjs-plugin-datalabels, @sgratzl/chartjs-chart-boxplot |
| HTML Parsing     | html-react-parser                                                                    |
| Bundler          | esbuild                                                                              |
| Testing          | Jest 29, jest-environment-jsdom, jest-canvas-mock                                    |
| Transpilation    | Babel (preset-env)                                                                   |
| Formatting       | Prettier (single quotes, tab width 4)                                                |
| Deployment       | gh-pages                                                                             |

## Commands

```bash
npm run build          # Bundle + format + test + link bundles (full build)
npm run bundle         # esbuild: src/main.js → index.js (+ sourcemap)
npm test               # Jest test suite
npm run test:coverage  # Jest with coverage report
npm run format         # Prettier: format src, examples, tests
npm run local          # live-server dev server
npm run watch          # esbuild watch mode
npm run deploy         # Deploy examples to gh-pages
```

### Module Pattern

Each chart type follows a consistent pattern:

- **Entry file** (`src/<chartType>.js`) — exports the public API
- **Module directory** (`src/<chartType>/`) — contains internal implementation files
- **Data transforms** — pure functions that process input data
- **Config builders** — functions that produce Chart.js or D3 configuration objects
- **Chart renderers** — functions that render charts to canvas/SVG via Chart.js or D3

## Code Conventions

- **Formatting:** Prettier with single quotes, tab width 4
- **Modules:** ES module syntax (`import`/`export`)
- **Naming:** camelCase for files and variables
- **Global export:** `gsmViz` (via esbuild `--global-name`)

## Mandatory Development Rule: Test-Driven Development

**All code changes MUST follow Red/Green/Refactor TDD. This is non-negotiable.**

### The Cycle

```
1. RED    — Write a failing test that describes the expected behavior
2. GREEN  — Write the minimum code to make the test pass
3. REFACTOR — Clean up the implementation while keeping tests green
4. VERIFY — npm test passes, npm run bundle succeeds
5. COMMIT — Save progress with a descriptive message
```

### Rules

- **No implementation code without a failing test first.** Write the test, see it fail, then implement.
- **Bug fixes require reproduction tests.** Write a test that demonstrates the bug (Red), then fix it (Green). This is the Prove-It Pattern.
- **Tests are evidence.** "It works" is not sufficient. A passing test suite is required proof.
- **Test framework:** Jest with jsdom + jest-canvas-mock. Tests live in `tests/`.
- **Run tests:** `npm test` after every change.

### Test Pyramid

```
80% Unit tests    — Data transforms, config builders, utilities
15% Integration   — Component rendering, data pipeline
 5% E2E           — Full chart rendering with real data
```

## Core Operating Behaviors

These apply at all times, across all tasks:

1. **TDD Always** — Write failing test first, then implement. No exceptions.
2. **Surface Assumptions** — State assumptions explicitly before implementing. Don't silently fill in ambiguous requirements.
3. **Manage Confusion** — Stop when confused. Name the confusion. Ask. Don't guess.
4. **Push Back** — Point out problems directly. Sycophancy is a failure mode.
5. **Enforce Simplicity** — Prefer the boring, obvious solution. If 100 lines suffice, don't write 1000.
6. **Scope Discipline** — Touch only what the task requires. No unsolicited renovation.
7. **Verify with Evidence** — Tests passing, build succeeding. "Seems right" is never done.

## Boundaries

### Always Do

- Write a failing test before implementation (TDD)
- Run `npm test` before commits
- Follow existing module patterns in `src/`
- Use Prettier formatting (single quotes, tab width 4)
- Write descriptive commit messages with type prefixes
- Keep changes small (~100 lines per commit)

### Ask First

- Adding new dependencies
- Changing build configuration (esbuild, Babel)
- Modifying shared utilities (`src/util/`, `src/data/`)
- Changing the Jest configuration
- Creating new chart type modules

### Never Do

- Commit secrets, credentials, or real clinical data
- Edit bundled output (`index.js`) directly
- Remove failing tests without approval
- Skip TDD for any code change
- Push to `main` without review
